## 01 — Feel Real

[`01-feel-real.md`](./results/01-feel-real.md)

**Question:** What actually makes a synthetic enterprise environment feel real to builders?

**Thesis:** Verifiable *operational depth* beats UI polish. Because Jungl3 installs into the customer's AWS account, engineers will inspect the underlying infrastructure, so the highest-signal realism cues are the ones that can be verified with AWS-native tools. The top three cues, ranked: (1) immutable, queryable **audit trails** (e.g., CloudTrail → S3 with Object Lock); (2) **roles and permissions** enforced at the backend (a forbidden action must yield a real 403, not a UI message); (3) **queues, backlogs, retries, and DLQs** that produce a rich ecosystem of CloudWatch metrics and logs. "Theatrical" cues to avoid: decorative service maps, untraceable dashboards, and placeholder data like "John Doe" or "lorem ipsum."

**Recommended v1 threshold:** 8–12 microservices, 4–5 distinct user personas, human-scale bursty event rates, and a **generative engine** behind every visible state.

## 02 — Domain Anchor

[`02-domain-anchor.md`](./results/02-domain-anchor.md)

**Question:** What is the best v1 domain anchor?

**Thesis:** Among the candidate anchors (insurance-like case processing, chargeback/dispute handling, benefits enrollment, order exception, loan/application review, permit/compliance), the strongest choice is **claims-adjacent workflows specifically expressed as e-commerce chargeback / dispute handling**. Rationale: it preserves the regulated feel and multi-actor handoff structure of insurance claims while using data, personas, and integrations (payment gateways, merchant portals) that are broadly familiar and low-risk — no PHI, no real financial exposure, lower plausibility bar per engineering dollar. Insurance claims proper are also viable but carry higher domain-specificity cost and a narrower stakeholder pool.

**Recommendation:** Pick **chargeback/dispute handling** as the v1 anchor. (Note: this recommendation is not yet reconciled with reports 10 and 11, which assume insurance claims throughout. See [`SYNTHESIS.md`](./SYNTHESIS.md) §Divergences.)

## 03 — MVR Threshold

[`03-mvr-threshold.md`](./results/03-mvr-threshold.md)

**Question:** What is the *minimum viable realism* threshold — the floor below which the environment will not feel real?

**Thesis:** Realism is a multi-axis floor, not a single number. A first Jungle that ships below this floor on any axis will feel fake regardless of how strong the others are.

**Recommended floor:**

- **4–7 microservices** with real inter-service calls (below 4 feels monolithic; above 7 adds complexity without more plausibility).
- **3–5 distinct user personas/roles**, with backend-enforced authz.
- **3–5 background jobs / async event types** producing visible queue activity.
- **2–4 intentionally visible stubs** (external integrations) with inspectable state.
- Inspectable **audit trail**, **feature flags**, and **at least one dashboard** seeded with real metric history.
- **Seeded data older than the install** — nothing starts empty.

Everything else (more services, more personas, more realism levers) is polish beyond the floor, not prerequisite to it.

## 04 — Synthetic Data

[`04-synthetic-data.md`](./results/04-synthetic-data.md)

**Question:** How should synthetic data be generated so it is plausible without being fake?

**Thesis:** Event-first, hybrid generation. Synthetic data is produced by running **Scenario Packs** — parameterized, seed-controlled scripts that drive entities through event sequences — rather than by inserting static rows. This ensures the data *has a history* (audit trails, state transitions, timestamps that line up) rather than appearing fully-formed. Free-text fields (notes, emails, descriptions) are generated by LLM behind a gateway with mandatory PII scrubbing and cost guardrails. Names, addresses, phone numbers are synthesized from aggregated census distributions and pinned to safe-by-construction domains (e.g., `@example.invalid`, 555-area-code phones). Timestamps follow diurnal/weekly/seasonal patterns, not uniform distributions.

**Recommendation:** Commit to an event-sourced generation pipeline with Scenario Packs, deterministic `run_seed`s for reproducibility, and a **Realism Score** self-check (Kolmogorov-Smirnov, autocorrelation, n-gram entropy) surfaced in the admin UI.

## 05 — Event / Workflow

[`05-event-workflow.md`](./results/05-event-workflow.md)

**Question:** What event and workflow patterns are essential to create operational life?

**Thesis:** Six patterns together produce the "lived-in system" feel. In priority order: (1) **state-machine-driven workflows** (orchestrated, not choreographed) for any multi-step business process; (2) **retries with exponential backoff** that produce visible log trails; (3) **Dead-Letter Queues** with a real redrive path in the admin UI; (4) **transactional outbox** so state changes and events never diverge; (5) **scheduled jobs** (cron/EventBridge) producing diurnal background activity; (6) **manual-review loops** with human-in-the-loop approvals via Step Functions' `waitForTaskToken`. Every event must carry an `eventId` (for idempotency), a `correlation_id` / `case_id` (for business tracing), and conform to a **CloudEvents** envelope with reverse-DNS type names.

**Recommendation:** Step Functions as the default orchestrator; EventBridge as the event bus; SQS + DLQ as the messaging primitive; outbox pattern enforced at the ORM/DAL layer.

## 06 — Stubs

[`06-stubs.md`](./results/06-stubs.md)

**Question:** How should stubs and simulators for external integrations be designed?

**Thesis:** Stubs are not mocks — they are **simulators**. A v1 stub must be **stateful** (remembers prior calls within a session), **declarative** (YAML/JSON mappings, not hand-coded handlers), **glass-box** (admin UI shows current state, traffic history, configured faults), and **swappable** (config flip to point at a real vendor without changing calling code). Fidelity comes in tiers: Wire (protocol-accurate), Behavioral (state transitions match), Integration (full flows with faults and latency). v1 ships Integration-grade for 2–4 external systems.

**Recommendation:** Build a generic declarative stub framework (WireMock/Prism-inspired, HTTP API behind Lambda) plus a curated catalog of pre-built stubs (payment gateway, OAuth2 IdP, doc storage, credit bureau). Support scenario state machines, response templating, fault injection (configurable error rate, latency distribution), and bindings to seeded data.

## 07 — Packaging

[`07-packaging.md`](./results/07-packaging.md)

**Question:** What is the right AWS Marketplace packaging and deployment strategy?

**Thesis:** **Hybrid compute, dual IaC, two-stage guided install.** Compute should mix Lambda (for spiky/async workloads) with ECS/Fargate (for long-lived/high-throughput services); a single-runtime choice is wrong for v1. IaC should be **CloudFormation as the primary published artifact** (Marketplace requires this), with Terraform as an optional secondary for customers who already standardize on it — both generated from a single source of truth (CDK). Installation is two-stage: (1) a lightweight bootstrap stack creates the customer-owned IAM role, KMS key, and S3 bucket; (2) a guided installer wizard (running in the customer's account) collects parameters and launches the full stack.

**Recommendation:** CloudFormation-primary, CDK-authored, Fargate+Lambda hybrid, two-stage guided install. Support single-account and Control Tower scenarios at launch; defer multi-region.

## 08 — Cost Floor

[`08-cost-floor.md`](./results/08-cost-floor.md)

**Question:** What does a Jungl3 install cost at idle and under load?

**Thesis:** A naïvely-architected install will cost **$400–$800/month at idle**, which is fatal for a prototype environment. A disciplined install can hit **$110–$150/month** at idle in the recommended "Default-Realism" profile. The cost drivers, in order of magnitude: (1) **NAT Gateway** (~$32/month per AZ, often overprovisioned); (2) **OpenSearch** (cluster minimum ~$70/month even empty); (3) **CloudWatch Logs ingestion** (verbose logging compounds fast); (4) **RDS/Aurora minimums**; (5) idle Fargate services. Mitigations: single-AZ NAT in dev, defer OpenSearch (use CloudWatch Logs Insights until customer opts in), aggressive log-class tiering (Standard vs Infrequent Access), Aurora Serverless v2 with scale-to-zero, AWS Budgets shipped by default.

**Recommendation:** Ship three cost profiles — **Demo** ($40–60/mo, ephemeral), **Default-Realism** ($110–150/mo, steady state), **Stress** (opt-in, $400+/mo). Default budget and alarms in every install.

## 09 — Observability UX

[`09-observability-ux.md`](./results/09-observability-ux.md)

**Question:** What should the observability UX for builders look like?

**Thesis:** A **custom, opinionated admin surface is mandatory**, not bloat. Relying on raw AWS consoles (CloudWatch, X-Ray) presents the product as a "box of parts" and guarantees plausibility collapse on first use. Strategy is hybrid **Build+Link**: build the business-context-aware views that generic tools cannot — **per-entity (case) timeline**, **queue health with business framing**, **failure inspection with one-click replay** — and deep-link into AWS consoles or third-party tools (Grafana, Honeycomb) for low-level trace/log analysis. Correlation model is **dual ID**: technical `trace_id` (W3C) + business `case_id`, both propagated through every hop. Observability stack defaults to ADOT → CloudWatch/X-Ray, with an opt-in OTLP export path. Destructive actions (replay, purge, DLQ redrive) require backend-enforced RBAC, dry-run preview, and immutable audit records with a `replayId`.

**Recommendation:** Build the three custom views in v1; provision a baseline CloudWatch dashboard, alarms, and log query definitions via CloudFormation; standardize on OpenTelemetry instrumentation; default-off telemetry-to-vendor.

## 10 — Personas

[`10-personas.md`](./results/10-personas.md)

**Question:** How do we achieve persona and workload realism without falling into plausibility collapse?

**Thesis:** Personas need four dimensions, not one: **identity** (name, contact, demographics), **owned workload** (active cases, pending approvals, drafts), **activity rhythm** (work hours, reply latencies, diurnal patterns), and **contextual artifacts** (email threads, audit entries, attachments implying prior engagement). v1 needs **8–10 personas** covering the core claims-processing roles (Intake, Triage, Junior/Senior Adjuster, Approver, Fraud/SIU, CSR, SysAdmin/Auditor). Each persona ships pre-seeded with a realistic portfolio (e.g., an adjuster starts with 40–100 active claims spread across states). Backlogs follow a **Nonhomogeneous Poisson Process** for arrivals and a **Lognormal-Pareto mixture** for service times, producing the 80/20 effort concentration real systems show. Friction is tunable (approval delays, evidence gaps, misroutes) with safety bounds to prevent demo-hostile dysfunction.

**Recommendation:** Implement the 8-role taxonomy, pre-seed each persona's workspace, model handoffs with Jira-style automation rules + SLA milestones + business calendars, use a hybrid simulation (Step Functions for deterministic golden paths + EventBridge/Lambda for stochastic background activity). Ship presets: Demo-friendly, Realistic Ops, Stress Surge, Auditor View.

## 11 — Regulated Cues

[`11-regulated-cues.md`](./results/11-regulated-cues.md)

**Question:** Which regulated-environment cues are real signal vs. ceremony, given v1 cost?

**Thesis:** Create the *atmosphere* of a regulated environment through high-signal, low-cost cues; defer expensive compliance ceremony. Ranked by realism-per-engineering-dollar: (Tier 1) append-only **audit trail with actor attribution** and **maker-checker approvals** backend-enforced; (Tier 2) **retention + legal hold UI flag** and **versioning with diffs**; (Tier 3) **document access logs**. Expensive features to **defer**: cryptographic WORM storage, enterprise PKI integration, granular cross-service RBAC engines, N-of-M approval workflows, automated compliance attestations (which are also legally perilous). Plausibility collapse detectors to guard against: missing/identical approver identity, identical or illogical timestamps, approvals-without-diffs, redactions without reason.

**Recommendation:** Build the Tier 1 + Tier 2 cues in v1. Use DynamoDB or Aurora (INSERT-only with triggers) for primary audit store; S3 + Object Lock (Governance mode) for archival and legal hold. Correlation IDs propagated through every request, job, and event. **Marketing language must avoid the words "compliant," "certified," "audited" — use "designed for," "supports," "tamper-evident."**

## 12 — Extension Model

[`12-extension-model.md`](./results/12-extension-model.md)

**Question:** How should the architecture support multiple domain variants over time?

**Thesis:** **Minimal core + versioned domain packs.** The shared core owns only cross-cutting concerns: deployment/lifecycle (CDK/CFN), AWS Marketplace entitlement, observability plumbing (OpenTelemetry), event envelope (CloudEvents), and generic runtimes for declarative stubs and seed data. All domain-specific logic — entity schemas, workflow definitions, personas, UI, scenario data — lives in versioned packs distributed as signed, immutable bundles via S3 (or OCI registry). Packs declare core-version compatibility (SemVer range); the in-account control plane verifies signatures and entitlements before installing. Runtime isolation is per-pack via resource prefixing (`jungle3-<pack_id>-*`) and scoped IAM.

**Recommendation:** Commit to the minimal-core + packs architecture *now*, even though v1 ships only one pack. The cost of deferring this boundary is a monolithic v1 that is structurally unextensible. Safe-to-build-now abstractions: CloudEvents envelope, minimal schema primitives (Case/Actor/Event/Document), declarative stub/seed formats. Dangerous-to-build-now: runtime plugin loader, hosted multi-tenant control plane, cross-domain analytics dashboard.
